# Map: calendarweek-tray v1

Type: wayfinder:map
Status: open

## Destination

A **locked implementation spec** for the v1 tray applet, plus a **visual prototype** that has settled the icon's rendered form. Reached when nothing remains to decide — an agent can build the whole thing in one session from the spec without asking a question.

## Notes

**Domain.** A Windows 11 notification-area applet showing the current ISO calendar week ("KW32"). .NET 10, WinForms `NotifyIcon` + GDI+ (`System.Drawing`) for glyph rendering. Runs as a windowless per-user background process — *not* a Windows Service, which cannot own a tray icon (session 0 isolation).

**Skills every session should consult.**

- HITL tickets: `/grilling` and `/domain-modeling`
- `wayfinder:prototype` tickets: `/prototype`
- `wayfinder:research` tickets: `/research`

**Standing preferences for this effort.**

- Minimal above all else. Every added key, file, or menu item must earn its place.
- **No third-party dependencies.** BCL + WindowsDesktop runtime only.
- No log file. Balloon tip for attention, hover tooltip for persistent state.
- The app **never writes** `config.json`. It runs correctly with no config file present.
- ISO 8601 week numbering is hard-wired (`ISOWeek.GetWeekOfYear`, never `Calendar.GetWeekOfYear`).

**This is a planning map.** Tickets produce decisions, not deliverables — with two deliberate exceptions: `05` scaffolds the project because nothing can be rendered without it, and `06` produces a prototype artifact because the visual question cannot be settled on paper.

**Environment facts already established.** .NET 10 SDK `10.0.301` is installed; the WindowsDesktop runtime is **`10.0.11`** (`07` — the map previously recorded 10.0.10). `SM_CXSMICON` reads **24** on this machine at 150% scaling. `Segoe UI Variable` ships as a single variable font (`SegUIVar.ttf`) but GDI+ enumerates named instances — `Segoe UI Variable Small` / `Text` / `Display`, each with Light/Semilight/Semibold. The repo now holds a **working scaffold** (`05`): one root-level `CalendarWeekTray.csproj`, exe `CalendarWeekTray.exe`, git on `main` with `origin` at `github.com/AckermannM/calendarweek-tray`. `10` re-measured the single-file publish at **194.3 KB** (`-c Release -r win-x64 --self-contained false -p:PublishSingleFile=true`), against `05`'s 168.8 KB — `08` should quote a figure it can reproduce. `Microsoft.DotNet.DesktopRuntime.10` is in the **winget catalogue at `10.0.11`**, matching the installed build. `%LOCALAPPDATA%\Programs` is a live convention here — 12 applications already install there.

## Decisions so far

- [01 — Charting decisions](issues/01-charting-decisions.md) — 23 design questions settled in one grilling session: hosting model, ISO numbering, config location and schema, click behaviour, DPI/theme handling, rollover, packaging, diagnostics.
- [02 — Taskbar clock font](issues/02-taskbar-clock-font-metrics.md) — the clock is **`Segoe UI Variable Small`, Regular 400, 12/16 epx** (the WinUI Caption ramp entry), and `Small` is correct for the tray glyph too. **GDI+ does not collapse the variable font's named instances** — verified by outline, pixel and advance-width diffs — so the "match the taskbar font" requirement survives. Three traps for the implementation: GDI+ **freezes the `opsz` axis** at the instance's value rather than varying it with size, so the optical variant must be chosen deliberately; **`new Font("Segoe UI Variable", …)` silently falls back to Microsoft Sans Serif** because the bare family the shell's XAML uses is not a GDI family; and `SPI_GETNONCLIENTMETRICS` reports legacy `Segoe UI` at every DPI, so the family must be hard-coded — though `lfMessageFont.lfHeight` does yield the correct DPI-tracking pixel size.
- [04 — NativeAOT viability](issues/04-nativeaot-winforms-viability.md) — **NativeAOT is unsupported, not merely risky**: `PublishAot` implies `PublishTrimmed`, which the .NET 10 SDK rejects with a hard `NETSDK1175` error for WinForms, escapable only via a private underscore-prefixed MSBuild property. The size prize doesn't exist either — forced-trim measured 36 MB and Microsoft's own issue reports 54 MB stock, against **195 KB** for framework-dependent single-file. Ship **framework-dependent single file**; this supersedes `01`/Q15's prototype-vs-ship split, since they turn out to be the same artifact. A forced-trim run proved the applet's whole API surface survives trimming — 21 of 22 checks passed, the sole failure being reflection-based `System.Text.Json`, fixed in-process by the source generator.
- [05 — Scaffold the project](issues/05-scaffold-project.md) — **the harness exists and works**: one root-level `CalendarWeekTray.csproj` (no `src/`, no `.sln`), `ApplicationContext` + `NotifyIcon` with no `Form`, building with **0 warnings** and confirmed live in the tray with a clean quit and no ghost icon. Four facts out: single-file publish measures **168.8 KB**, vindicating `04`; `IsAotCompatible` analyzers are **silent**, not noisy; PerMonitorV2 is declared via the `ApplicationHighDpiMode` MSBuild property with **no `app.manifest`**, which `07` may revise; and — the sharp one — **`TextRenderer` cannot draw onto a transparent bitmap**, because GDI text has no alpha, which collides directly with `07`'s lean toward `TextRenderer` for shell-matching fidelity.
- [06 — Icon layout prototype](issues/06-icon-layout-prototype.md) — the glyph is a **calendar page: square corners, 1 px outline, filled binding bar with two rings notched through it, week number in the body — unpadded, `Segoe UI Variable Text Semibold`, smooth `AntiAlias`**. `KW` appears nowhere: it lost on one line, stacked at four different sizes and weights, beside the number, and knocked out of the bar. Both layouts this ticket set out to choose between lost, and the ticket's recorded prior was backwards — `Single` collapsed, not `Stacked`. The unlock was measuring that digit size is constrained by **width, not height**, so a cue above the digits is nearly free. Four bugs fixed on the way, all of which would otherwise have reached the spec: `05`'s glyph was rendering with **no antialiasing at all**; `SystemDefault` is a trap that emits ClearType colour onto a transparent icon; the fit reference `"00"` was **not the widest label** (figures are proportional — `"44"` is, and weeks 4/14/24/34/40–49 were overflowing); and the number was off-centre both from banker's rounding and from the deeper error of predicting a draw offset instead of measuring where the ink landed. Also settles for `07`: **`GetHicon` preserves partial alpha**, so `05`'s alpha worry and its `TextRenderer` constraint are both moot.
- [03 — Run key / StartupApproved](issues/03-run-key-startupapproved.md) — rewriting our Run value **cannot** silently re-enable a Task-Manager-disabled entry: the approval blob is keyed by value name, is written only by GUI startup managers or the app itself, and survives identical rewrite, changed-path rewrite, and delete-and-recreate as a durable tombstone. Autostart strategy is **self-register once, guarded** by three registry reads and no written state. Two constraints for the spec: `Win32_StartupCommand` ignores `StartupApproved` and must never be used as an "am I enabled?" oracle, and Autoruns disables by moving the value to `Run\AutorunsDisabled` instead, which the guard must also check.

- [07 — Rendering pipeline and lifetime](issues/07-rendering-pipeline-and-lifetime.md) — **one idempotent `Reconcile()` behind every trigger**, comparing a desired `(week, sizePx, ink, tooltip)` tuple against what is displayed; the 60 s timer is the safety net and every event merely advisory. Three types: a pure `GlyphRenderer.Render(GlyphSpec) → Bitmap` holding all of `06`'s rules, a `GlyphIcon : IDisposable` owning `(Icon, HICON)` as one unit, and the context. Measured: each `GetHicon` costs **3 GDI + 1 USER** object that **the GC never reclaims**, so a forgotten `DestroyIcon` exhausts the 10,000 limit in ~3,300 renders — two and a half days if a bug made it fire per minute. Live-tested: **`NotifyIcon` re-adds itself on `TaskbarCreated` unaided** — proven against a hand-registered control icon that never returns — with a ~4 s gap during which **`_added` lies**; **`SystemEvents` fires on a background thread** with the uninformative `General` category, so marshalling is mandatory and filtering pointless; **a registry theme write that broadcasts nothing produces no event at all**, so only the poll catches it; and **`SynchronizationContext.Current` is the wrong context inside the constructor**, posting to the thread pool unless captured on the first timer tick. Also: `NotifyIcon.Text` holds **127** characters, not `01`'s 63. Orphaned three of `01`'s four config keys (→ `14`) and gave the testing fog its seams (→ `15`).

- [09 — Autostart deregistration](issues/09-autostart-deregistration.md) — **the applet registers, it never governs**: one `REG_SZ` written at most once, and **`StartupApproved` is never written in any code path**. The ticket's own recommended answer turned out to be self-defeating — deleting the `Run` value is undone by `03`'s guard on the very next launch, which dissolves the (a)/(b) split into "write the tombstone or have no deregistration", and ruling out the tombstone left only the latter. `StartupApproved` writing was rejected because `03` graded the byte semantics **medium-high** off an archived forum post, and that soft link is exactly what a *writer* leans on while a presence-checking *reader* is immune; the Docker Desktop precedent doesn't transfer, since Docker writes the blob to sync an in-app AutoStart checkbox we will never have. Five things for `08`: registration is **Release-only** (a debug run would otherwise leave a dead `Run` value pointing at `bin\Debug\` that nothing ever mentions), the path must come from **`Environment.ProcessPath`** because `Assembly.Location` is **empty under single-file**, the data is **quoted** with **no arguments**, a failed write is **swallowed silently** and documented in `README.md` instead, and the guard **fails closed** on any read exception. Also overturned `03`'s stale-path surfacing rule — the applet reports **nothing** about its autostart state — and pushed uninstall wholesale to `10`.

- [10 — How does the applet get onto a machine?](issues/10-distribution-and-install.md) — **a zipped exe on a GitHub Release, and everything else is documentation**: no winget manifest, no signing, no updater, no installer, and the whole of this ticket's surface is `README.md` plus a `<Version>` property. The reshaping finding was **measured, not argued** — the ticket's premise that a missing runtime "silently fails" is false: the single-file artifact run with no framework visible shows a native apphost task dialog with a one-click **"Download it now"** button, because the error is raised *before* managed code exists and so escapes `09`'s "a `WinExe` can never report anything" constraint. That collapsed the runtime question to one README line and removed winget's only real argument. Install location is **`%LOCALAPPDATA%\Programs\CalendarWeekTray\`, recommended and never enforced** — enforcing it would be *governing*, which `09` denied the applet — and it reconciles `03`/`09`/`10` without changing a line of code, since the convention lives only in the README. Its payoff is update-correctness: replacing the exe **in place** is what preserves both the `Run` value and `11`'s `NotifyIconSettings` promotion. Uninstall is four documented manual steps, the `StartupApproved` tombstone deliberately left. Also measured: single-file is **194.3 KB**, not `05`'s 168.8 KB, and `Microsoft.DotNet.DesktopRuntime.10` is in winget at `10.0.11`.

- [11 — Notification-area promotion](issues/11-notification-area-promotion.md) — **the icon starts in the overflow flyout, the applet can promote itself, and it must not**. Measured on a never-before-seen path: the shell writes no `IsPromoted` value at all on first run, and the glyph was visually confirmed as the flyout's first entry while the tray held only PowerToys — so `05`'s `IsPromoted=1` was **the user's own drag**, not the shell's default, and the map's original fog assumption was the correct one. Microsoft has documented since Windows 7 that "only the user can promote an icon from the overflow"; Windows 11 replaced the *store*, not the *policy*, and no promote flag exists anywhere in `NOTIFYICONDATA`. The unsupported registry poke nevertheless works **live, within 2 s, with no app or explorer restart** — so this is a "we checked and chose not to", not a "we couldn't". It was rejected because it is `09`'s posture again (the applet shows an icon; it never decides where the icon lives) and because it is unreliable exactly where it would need to work: the subkey name is a deterministic but **undocumented** hash of the exe path, so the applet must scan for its own `ExecutablePath` — and after the key was deleted under a running shell that value **never came back**, not after 100 s of polling nor an applet restart, because the shell serves from memory and re-persists only on first sight of an exe. Confirms `10` without changing it: two coexisting keys for the same binary at two paths prove the move-resets-promotion rule `10` assumed, and make its **versionless** install directory load-bearing rather than incidental. The whole deliverable is a **first-run README paragraph**, which belongs right after *Install* — an applet meant to be read at a glance is not degraded in the flyout, it is pointless — plus a spec line recording the non-behaviour: the applet never reads or writes `NotifyIconSettings`.

- [12 — Does the icon need a reduced form at 16 px?](issues/12-sixteen-px-reduced-form.md) — **one form at every size**: `06`'s `FrameRings` renders at whatever `SM_CXSMICON` reports and nothing about the glyph is size-dependent, which is the cheap answer `08` can now rely on. The ticket's keep-or-drop binary turned out to be genuinely binary, because a third option it did not contain was rendered and died on measurement: the frame's 2 px cost is two constants — a 3 px bar and 1 px of inner air — and opening them up recovers **1 px of the 2**, unusably. The thinner bar buys **nothing at all**, which is `06`'s width-not-height finding cutting a second way — giving vertical space back is inert. Dropping the inner air puts the `4`s directly against the side outline (measured gap 0 both sides on week 44) where they visibly fuse, and shifts week 11's stems onto a subpixel phase that renders them grey. So `bar = 0.17` and `air = 1 px` are **load-bearing constants, not tuning**. Two facts out: the single-pixel ring slots at 16 px are **crisp — not one partial alpha pixel**, so `06`'s snapping holds where the ticket said verify rather than assume; and the number **never matches the clock at any size**, framed (66–75%) or bare (83%), so parity was never on the table and 16 px is the worst case only marginally. Constrains `13`: dropping the frame is no longer available as a text-scaling response.

- [13 — Accessibility: text scaling, and high contrast](issues/13-text-scaling.md) — **text scaling is ignored, high contrast is not**, and the two halves diverge because what matters is not what the setting does but what the *taskbar* does. The reshaping finding killed the ticket's own premise: the taskbar is **immune to text scaling**, so the clock beside the glyph does not grow either and responding would make the applet the only thing on the bar that did. Measured in two steps so a null result could not be dismissed — writing `TextScaleFactor` moves `UISettings.TextScaleFactor` 1→2 in three seconds, and yet an exact pixel diff of `Shell_TrayWnd` shows **0 of 184,320 pixels differing** at 200% and at 225%, against a **0-pixel control**. `SM_CXSMICON` never moves. So "deliberately nothing" is not the concession `12` left it as: spending digit height here would be wrong at any budget. The other half is a defect caught before shipping — **`SystemUsesLightTheme` reads `0` under all four stock contrast themes**, so `07`'s rule paints `#FFFFFF` on High Contrast White's `#FFFAEF` at **1.04:1, an invisible icon**, undetectable from that key alone. The fix is `HighContrast ? SystemColors.MenuText : 07's rule` — **`MenuText` is the only palette entry matching the shell's own measured taskbar ink 4/4**, where the ticket's suggested `WindowText` misses on HC White and `ControlText` is an accent (cyan under #1, yellow under #2). The rule must stay conditional because **`SystemColors` does not track dark theme at all** — unconditional `MenuText` is 1.29:1 on a normal dark bar, the same bug moved. **High contrast wins over the `theme` key outright**, including an explicit `light`/`dark`, since the key exists to correct a mis-read the palette makes impossible; `theme` keeps three values and needs no fourth (for `14`). Also closed `12`'s one open lever: heavier weight buys nothing, so **`06`'s Semibold stands at every size and in every theme**.

## Out of scope

- **Hosting as a Windows Service** — ruled out by fact, not preference: session 0 isolation makes tray icons impossible from a service.
- **Placing the icon adjacent to the clock** — that region is reserved for system status. Ruled out by the user in the original brief.
- **Non-ISO week numbering** (US broadcast week, etc.) — German business practice is ISO 8601 via DIN 1355-1, so ISO is the only scheme v1 needs. A different scheme would be a fresh effort.
- **Languages beyond `de` and `en`** — the `label` override makes arbitrary prefixes possible without new locales, which closes this permanently.
- **Auto-reload via `FileSystemWatcher`** — debouncing, partial-write races, and save-by-rename editors buy complexity the explicit "Reload config" menu item avoids.
- **A log file** — balloon tip plus hover tooltip is the entire diagnostic story.
- **Making the font configurable** — the taskbar font is a requirement of the brief, not a preference; exposing it invites breaking the one thing that makes the applet look native.
- **Autostart deregistration in any form** — no `--unregister` flag, no menu item, no deregistration code ([`09`](issues/09-autostart-deregistration.md)). Task Manager is the sole off-switch and a complete one, since `03` proved its disable survives every rewrite. Deleting the `Run` value without writing a tombstone is undone by the guard on the next launch, and writing the tombstone was ruled out separately — so the feature had no coherent form left.
- **Authoring `StartupApproved` blobs** — the applet reads that key and never writes it, including on uninstall ([`09`](issues/09-autostart-deregistration.md)). Ruled out on evidence quality: the format is undocumented by Microsoft and `03`'s byte semantics rest on an archived MSDN forum post. This closes semantic (a) — "stay listed in Task Manager but disabled" — permanently; Task Manager already provides it natively.
- **A winget manifest** ([`10`](issues/10-distribution-and-install.md)) — the one option that could declare the runtime dependency, and the measurement that the apphost already explains a missing runtime with a one-click download button took its only real argument away. What remains is a manifest PR to `microsoft/winget-pkgs` per release and a version bump that must never be forgotten — a recurring obligation, which is the category this effort refuses.
- **Code signing** ([`10`](issues/10-distribution-and-install.md)) — ruled out on merit, not just cost. An OV certificate is an annual charge *and* must still accrue SmartScreen reputation across downloads before the warning stops, which an applet with three users will never earn; only EV clears it immediately. Paying yearly for a warning that persists anyway is the worst outcome available. The README names the *"More info → Run anyway"* click-path instead.
- **Any update mechanism** ([`10`](issues/10-distribution-and-install.md)) — no self-updater, and not even a passive check for a newer release tag. The passive form was weighed separately and rejected because it would give the applet a network dependency it does not currently have, in order to report a version the user must still install by hand. Updates are: quit, replace the exe **in place**, run.
- **An installer, and enforcing the install location** ([`10`](issues/10-distribution-and-install.md)) — the canonical directory is recommended in the README and never checked. Enforcement means the applet inspects `Environment.ProcessPath` and complains, which is *governing* — the posture `09` denied it — and would add a startup failure mode to an applet whose entire diagnostic story is a balloon tip.
- **Self-promotion out of the notification-area overflow** ([`11`](issues/11-notification-area-promotion.md)) — the applet never reads or writes `HKCU\Control Panel\NotifyIconSettings`. Ruled out despite the poke being *measured to work*: promotion is the user's decision by Microsoft's own guideline, doing it anyway is *governing* — the posture `09` denied the applet — and the mechanism is an undocumented path-hash lookup whose anchor value the shell does not reliably persist. Two clicks by the user, documented, against a poll loop and a failure mode.

- **Shipping `.pdb` symbols in the release zip** ([`10`](issues/10-distribution-and-install.md)) — there is no log file, no crash reporting and no support channel to send a stack trace to, so 22.9 KB of symbols serves nobody. The matching build stays available locally.
